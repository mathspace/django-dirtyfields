# django-dirtyfields threat model

## Overview

An in-process Django model mixin snapshots model values and compares them with later in-memory state. It supports selective update_fields saves, optional M2M comparisons, and a queryset path that disables tracking. It owns no HTTP endpoint, user identity or separate storage service (src/dirtyfields/dirtyfields.py:25; src/dirtyfields/dirtyfields.py:57; src/dirtyfields/dirtyfields.py:222).

The library runs with the same authority as the host Django model. A caller can inspect dirty values, ask whether an instance changed, or save the changed fields. It does not expose a listener, issue credentials, install a tenant model or create an independent audit store. Querysets and model initialization determine tracking state. Ordinary from_db explicitly passes None, and DirtyFieldsQuerySet defaults its flag to False; both bypass a class DISABLE_DIRTYFIELDS=True default and enable tracking on loaded instances. Only construction without an explicit flag falls back to that class setting, so verify the actual load path and use explicit disabling where required, subject to the disabled-save lifecycle limitation (src/dirtyfields/dirtyfields.py:38; src/dirtyfields/dirtyfields.py:69-98; src/dirtyfields/django_patches.py:79-105). Security relevance arises when a host uses these results for persistence decisions or sends them to a less-trusted recipient.

## Threat Model, Trust Boundaries, and Assumptions

**Protected assets.** Original and current field values held in process memory, possibly confidential when models contain personal data (src/dirtyfields/dirtyfields.py:165). Correct selective persistence of caller-owned model fields and model baseline lifecycle (src/dirtyfields/dirtyfields.py:222; src/dirtyfields/dirtyfields.py:227).

**Actors and starting authority.** Untrusted input can affect model values only through a host integration; the library does not grant outsiders an object reference or mutation authority. A caller controlling normalization/comparison functions already supplies executable application code.

**Trust boundaries and owned controls.**

- Trusted model construction connects post_save and optionally m2m_changed; reset_state refreshes local baselines. The queryset disable flag is not a permission boundary. Once an enabled instance registers the class-wide post_save receiver, an ordinary save of a disabled instance still reaches reset_state and raises DirtyFieldsDisabled through the guarded _as_dict. Under autocommit the database write can persist despite the save raising; an enclosing transaction changes recovery semantics (src/dirtyfields/dirtyfields.py:40; src/dirtyfields/dirtyfields.py:69-83; src/dirtyfields/dirtyfields.py:120-121; src/dirtyfields/dirtyfields.py:227-231; src/dirtyfields/decorators.py:12-18).
- Only a nonempty FIELDS_TO_CHECK filters eligible fields; None and an empty collection both disable filtering rather than select zero fields, including in optional M2M capture. Deferred and expression values are still skipped, and included values are converted and deep-copied. Ordinary fields incur two deepcopy calls to the same dictionary key, discarding the first result, during initialization/reset and dirty checks (src/dirtyfields/dirtyfields.py:165-166, src/dirtyfields/dirtyfields.py:188-198, src/dirtyfields/dirtyfields.py:231). Large mutable payloads and many loaded/checked rows can amplify CPU and peak memory independently of M2M; immutable scalar/bytes values may be reused, so no uniform allocation multiplier is implied. Bound host payload/cardinality, use a nonempty tracked-field restriction or avoid unnecessary tracking, and measure representative snapshot/check costs. For no disclosed fields, return no dirty-field data or enforce an independent caller output allowlist; for no snapshots on a read-only path, explicitly disable tracking and verify that load path, retaining the documented disabled-save caveat. No empty FIELDS_TO_CHECK configuration provides track-none semantics (src/dirtyfields/dirtyfields.py:127; src/dirtyfields/dirtyfields.py:176; src/dirtyfields/dirtyfields.py:236). Configured compare/normalise functions execute with caller process authority (src/dirtyfields/dirtyfields.py:58; src/dirtyfields/dirtyfields.py:121).
- For saved instances, get_dirty_fields returns saved values by default or saved/current pairs in verbose mode. For unsaved instances (_state.adding), every included field is dirty: default output contains current values and verbose output contains saved: None/current pairs; field-selection rules still apply (src/dirtyfields/dirtyfields.py:185-193); callers decide whether those values reach logs, APIs or telemetry. save_dirty_fields delegates to self.save(update_fields=...) and is intended for an already-persisted instance, not initial insertion. Under Django 1.11, with nonempty selected fields, an unsaved instance without a PK raises under forced-update semantics. An assigned PK is included in dirty output by default, causing update_fields validation to raise ValueError because primary keys are not updatable fields. Only when the tracked-field selection excludes the PK can an assigned PK reach a forced update: no matching row fails, while a matching row can be updated (src/dirtyfields/dirtyfields.py:188-193; [Django 1.11.29 Model.save and _save_table](https://github.com/django/django/blob/1.11.29/django/db/models/base.py)). Empty selected fields can instead yield no save. Perform an ordinary authorized initial save before selective updates; model authorization and transactions remain host responsibilities (src/dirtyfields/dirtyfields.py:184; src/dirtyfields/dirtyfields.py:222).

- With ENABLE_M2M_CHECK enabled and its receiver registered, a reverse-manager relation update can supply a related instance lacking DirtyFieldsMixin to reset_state. The receiver ignores reverse/action and calls instance._as_dict unconditionally, raising instead of completing that supported relation operation. If the reverse-side instance instead has enabled DirtyFieldsMixin tracking, reset_state can succeed and replace its ordinary baseline with pending unsaved scalar edits; later save_dirty_fields then omits them. This also occurs when that related model does not itself enable M2M checking, because the already-connected receiver still resets its scalar state. Persist intended scalar edits before relation mutation or restrict the receiver to the appropriate instance/direction and M2M baseline without resetting unrelated fields. Avoid that reverse mutation path or disable optional M2M checking before receiver registration until the receiver explicitly handles direction/instance compatibility; do not assume an after-write commit because M2M signal timing and transaction handling differ from ordinary saves (src/dirtyfields/dirtyfields.py:81-83; src/dirtyfields/dirtyfields.py:115-118; src/dirtyfields/dirtyfields.py:227-231).

- The advertised Python 2.7/3.5 environments are incompatible with this source before queryset loading: dirtyfields.py imports decorators.py, whose f-string requires Python 3.6 syntax; django_patches.py also contains f-strings. Once prerequisite imports resolve, parsing the decorator module fails rather than reaching model operations. The queryset’s zero-argument super() is an additional Python 2 incompatibility if earlier import failures are removed. Choosing Django 2.0/2.1 alone cannot establish Python 3.5 compatibility. Validate the actual Python/Django combination and reconcile the advertised support matrix before integration (tox.ini:4-6; CLASSIFIERS.txt:6-15; src/dirtyfields/dirtyfields.py:14,28-30; src/dirtyfields/decorators.py:17; src/dirtyfields/django_patches.py:43; [Python 3.6 f-string introduction](https://docs.python.org/3/whatsnew/3.6.html#pep-498-formatted-string-literals); [Python 2.7 super contract](https://docs.python.org/2.7/library/functions.html#super)). On a compatible Python runtime under Django 1.11.29, the custom DirtyFieldsQuerySet loading path fails before model or related-instance construction: ModelIterable accesses self.chunk_size, which Django 1.11.29 BaseIterable does not define. Consequently, this version does not establish successful disable-flag propagation through select_related. Verify compatibility of the custom iterator with the actual Django version before relying on explicitly disabled querysets, then verify tracking state across the relevant loaded graph; retain the disabled-save lifecycle caveat (src/dirtyfields/django_patches.py:73-119; [Django 1.11.29 BaseIterable implementation](https://github.com/django/django/blob/1.11.29/django/db/models/query.py)).

- select_related has a distinct compatibility boundary once iterator construction succeeds: Django 2.0.13/2.1.15 initialize RelatedPopulator.local_setter/remote_setter, but this override still accesses cache_name/reverse_cache_name. A populated select_related query can therefore raise at cache assignment even without disabling tracking; nested graphs are not made compatible merely by resolving Django 1.11 iterator attributes. The inherited initializer constructs nested populators through Django’s own factory, so recursive propagation of this override’s disable flag is not established either. Adapt the populator to the installed Django cache API and verify one-level/nested loading and tracking state, or avoid this custom select_related path until compatible (src/dirtyfields/django_patches.py:15-55,58-67,95-119; [Django 2.0.13 RelatedPopulator](https://github.com/django/django/blob/2.0.13/django/db/models/query.py#L1770-L1799); [Django 2.1.15 RelatedPopulator](https://github.com/django/django/blob/2.1.15/django/db/models/query.py#L1815-L1843)).

- Forward M2M add/remove/clear events also reset the ordinary baseline: with ENABLE_M2M_CHECK and unsaved scalar changes, the unfiltered receiver can snapshot those changes as clean before they are saved, so later selective saving omits them. Persist intended ordinary changes before relation mutation, or use a receiver that updates only the M2M baseline at the appropriate action; do not infer scalar persistence from a reset (src/dirtyfields/dirtyfields.py:115-118, src/dirtyfields/dirtyfields.py:227-250).

- A save(update_fields=[field]) with an included F()/BaseExpression value can write successfully and then raise KeyError in post_save: _as_dict omits the expression while selective reset indexes it. Under autocommit the update may already be durable. Avoid this unsupported selective-expression path until reset handles omitted expression values; reconcile database state before retries and use an enclosing transaction with propagated errors when atomic failure is required (src/dirtyfields/dirtyfields.py:142-144, src/dirtyfields/dirtyfields.py:227-245). A successful full save without update_fields has a different failure: if an expression remains on the instance, _as_dict omits its field and full reset replaces _original_state without that key. A later concrete assignment is skipped by compare_states because the original key is absent, so get_dirty_fields reports no change for that field and save_dirty_fields omits it. After expression saves, rebuild the baseline from a verified full database reload before making subsequent edits; preserve/reconcile any already-pending edits separately and retain the partial-refresh caveat below (src/dirtyfields/dirtyfields.py:105-110,142-144,247-248; src/dirtyfields/compare.py:11-17; [Django F-expression persistence](https://docs.djangoproject.com/en/1.11/ref/models/expressions/#f-assignments-persist-after-model-save)).

- Configured normalization arguments are not applied uniformly. Saved non-verbose output normalizes in compare_states with kwargs, then normalizes again without them; unsaved verbose output omits kwargs, and unsaved non-verbose output bypasses normalization. Required arguments may raise, and defaulted conversion/redaction options can produce unintended output. Validate each used mode with its configured callable and enforce independent outbound field/redaction policy; do not treat normalise_function as a reliable confidentiality boundary (src/dirtyfields/compare.py:24-25, src/dirtyfields/dirtyfields.py:185-193, src/dirtyfields/dirtyfields.py:198-212).

- Optional M2M snapshots can amplify host request work: for an instance with a truthy PK, initialization and each enabled reset enumerate every eligible relation and materialize related objects into PK sets. Loading or saving many high-cardinality instances can multiply queries and memory use; existing relation caches may reduce queries but do not remove snapshot materialization. Bound host page/relation cardinality, restrict tracked fields and avoid M2M tracking on unnecessary load paths; measure representative query counts and memory before enabling it at scale (src/dirtyfields/dirtyfields.py:174-180, src/dirtyfields/dirtyfields.py:249-250; docs/index.rst:117-118).

- disable_dirtyfields() on a root queryset does not propagate to independently evaluated prefetch_related querysets. Related mixin instances can still retain snapshots and incur tracking work. Where the entire loaded graph must avoid tracking, supply explicitly disabled compatible querysets through Prefetch for each relevant prefetch path and verify actual loaded instances; retain the disabled-save lifecycle caveat (src/dirtyfields/dirtyfields.py:27-52, src/dirtyfields/django_patches.py:79-119).

- Selective foreign-key saves can leave a stale relationship-name baseline: snapshots store both field.name and attname, but selective reset updates only attname. Subsequent check_relationship=True comparisons can report the already-persisted FK as dirty and retrigger host saves/signals. Keep both aliases synchronized in reset or rebuild the baseline from a verified reload after persistence; avoid treating repeated relationship dirtiness as evidence of a new change (src/dirtyfields/dirtyfields.py:165-166, src/dirtyfields/dirtyfields.py:222-245).

- Partial refresh also loses dirty state: refresh_from_db(fields=[...]) refreshes selected fields, then this override resets the entire ordinary baseline. An unrelated unsaved value can become clean, so save_dirty_fields later omits it. Deferred-attribute access can trigger the same partial-refresh path. Preserve unaffected baseline entries and reset only fields actually refreshed; until corrected, avoid partial refresh/deferred loads while pending edits must remain dirty (src/dirtyfields/dirtyfields.py:105-110, src/dirtyfields/dirtyfields.py:227-248).

- Initial M2M snapshot routing precedes database-alias assignment: from_db constructs the instance, whose initializer captures relations, before setting new._state.db. For enabled tracking with a truthy PK loaded from a non-default database, default/custom relation-read routing can select another database while the source alias is unset, yielding wrong same-PK relation IDs, an empty baseline or a query error. Disclosure additionally requires exposing that wrong-database result through a host boundary. Defer initial relation capture until the source alias is installed and verify related-read routing; an explicit router may already avoid the mismatch (src/dirtyfields/dirtyfields.py:69-102, src/dirtyfields/dirtyfields.py:174-180, src/dirtyfields/dirtyfields.py:249-250).

- Valid falsey primary keys, such as integer 0 where accepted, skip all M2M snapshot capture because the guard is if self.pk. The resulting empty baseline causes compare_states to ignore supplied relation keys absent from the original state, so M2M changes can appear clean. Use an explicit None check and verify capture/comparison for supported PK values; until corrected, do not rely on M2M dirty results for affected objects or use them as an authorization boundary (src/dirtyfields/dirtyfields.py:174-180, src/dirtyfields/dirtyfields.py:204-208; src/dirtyfields/compare.py:11-17).

- Selective saving fixes update_fields before model save overrides and pre_save receivers run. When such a hook changes an initially clean field without expanding the selection or explicitly persisting it, the in-memory value can differ from the database and a hook-enforced audit/approval invariant can be omitted. Include all required hook-owned fields before the ORM save, for example by a save override that expands update_fields before super(), or persist them explicitly with appropriate transaction handling. A pre_save receiver must not assume its mutation adds a field to the SQL update. If no fields were initially dirty, Django can skip saving/signals entirely (src/dirtyfields/dirtyfields.py:222-224).

**Security objectives.** Authorize assignment/persistence before invoking selective saves. Protect returned baselines and verbose diffs as sensitive model data. Do not use dirty state as a substitute for concurrency control, database truth or an audit ledger.

**Assumptions and unresolved controls.**

- Snapshots reflect instance lifecycle; concurrent external updates and transaction rollback semantics require caller design, not an inferred lock or transaction guarantee (src/dirtyfields/dirtyfields.py:227).
- Packaging uses setuptools for django-dirtyfields 1.3.1. The Travis deploy configuration publishes tagged builds from any branch to PyPI as user smn using an encrypted password reference. Current Travis activation, credential validity, tag protection and PyPI account controls are unknown; the checked-in publication path itself is established (setup.py:8; .travis.yml:57-64).
- No database endpoint, business transition policy, audit integration or log collector is supplied. M2M checks default off, relationship comparisons are optional, and deferred/expression values may be omitted; review a real consumer before assigning impact to those choices.

## Severity Calibration (Critical, High, Medium, Low)

| Level | Repository-specific example | Counterexample or limiting prerequisite |
| --- | --- | --- |
| Critical | A demonstrated host integration turns lower-trust callable/package selection into broad privileged code execution. | The repository supplies no remote callable-selection API; ordinary trusted Python customization is not a critical vulnerability. |
| High | A real host bypass permits unauthorized sensitive state changes or disclosure of another user’s confidential baseline. | Requires the host authorization boundary and concrete impact, not just detection of a changed field. |
| Medium | A supported caller workflow loses meaningful consistency or confidentiality because it misuses partial instance state. | Concurrency/transaction and data prerequisites must be shown; no general audit or lock guarantee is established. |
| Low | An isolated caller receives an unexpected dirty result or disabled-state error without shared-state or confidentiality impact. | Developer debugging and authorized local inspection of model values are expected behavior. |

This model uses an independent source-backed architecture pass. Repository citations were checked against the supplied inventory and source lines; application code and external services were not executed. Source-established behavior is distinct from unverified deployment exposure. Revisit the model when the described input, storage, authorization or publication boundaries change.
